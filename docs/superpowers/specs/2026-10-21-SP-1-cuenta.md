**Depende de:** SP-0 (T-039 runner Vitest/Playwright). **Paralelizable con:** SP-3.
**Orden interno:** T-040 → T-041 → T-042. Los tres nacen Strong: plan en `engram/plans/<T-ID>.md` antes de codear.

Hechos medidos en `4bd9f27` que fundan los tres tickets:
- "¿Olvidaste la clave?" es un `<span>` sin handler (`entrar/page.tsx:195-197`); no existe `resetPasswordForEmail` en `src`.
- El botón Google está `disabled` (`entrar/page.tsx:236-240`).
- El login hace `router.push("/panel")` siempre (`:89`); el `?next=` que pone `src/proxy.ts:36` se tira.
- `enable_confirmations = false` (`config.toml:228`); no hay ruta de callback; `additional_redirect_urls` tiene `https://127.0.0.1:3000` (esquema erróneo, sin `/auth/callback`).
- La bienvenida sale desde el cliente al registrarse (`entrar/page.tsx:86` → `entrar/actions.ts:17`), apoyada en que `signUp` deja sesión puesta. Con D8 eso deja de ser cierto.
- `profiles` la crea `handle_new_user` (`0002:107-124`, trigger `after insert on auth.users`, rol literal `student`). Ninguna action actualiza `profiles` salvo el cambio de rol del admin.
- Grants de `profiles` hoy: select `(id, role, full_name, slug, glyph, bio, created_at)` + públicos de `0011` a `anon, authenticated`; update `(full_name, slug, glyph, bio, headline, location, quote)` a `authenticated`. Policies: `profiles_read_public` (teacher/admin a todos), `profiles_read_self`, `profiles_update_self`.
- Supabase Storage no se usa en ningún lado. `00_supabase_baseline.sql` (PGlite) no trae el schema `storage`.
- `/guias/[slug]` muestra `glyph, full_name, headline, location, years_practice, bio, quote, formations, testimonials` y cursos. Sin avatar.

Los mails de GoTrue (confirmación, recuperación) salen por el SMTP propio de Supabase local (Mailpit, UI en 54324); los de la app salen por `SMTP_HOST` (54325, mismo Mailpit). Playwright lee los links desde la API de Mailpit.

## T-040 · Reset de contraseña, confirmación de mail y `?next=`

**Agente:** `nerv-web` + `nerv-arquitecto` (config/hook) · **Nivel:** Strong · **Depende de:** T-039

### Por qué
Hoy una alumna que olvida la clave no tiene salida, cualquiera puede crear una cuenta con un mail ajeno (y recibir la bienvenida en nombre de otro), y quien llega a `/entrar?next=/leccion/x` termina en `/panel`. D8 fija que la sesión existe recién después de confirmar.

### Qué se toca
- `supabase/config.toml`: `enable_confirmations = true`; `additional_redirect_urls = ["http://127.0.0.1:3000/auth/callback", "http://localhost:3000/auth/callback"]`; `[auth.rate_limit] email_sent` queda documentado (ver Riesgo).
- `src/app/auth/callback/route.ts` (nuevo, fuera de `(app)` y `(marketing)`): Route Handler GET. Lee `code` y `next`, crea el cliente de `@/lib/supabase/server`, `exchangeCodeForSession(code)`, redirige a `safeNext(next)`. Sin `code` o con error: redirige a `/entrar?error=link` con mensaje neutro.
- `src/lib/auth/safe-next.ts` (nuevo, módulo plano sin `server-only`, lo usan el callback y la página): acepta solo rutas relativas internas (`^/(?!/)`), descarta esquema, host, `\\`, y devuelve `/panel` en cualquier otro caso. Es el único saneador; el proxy y las pantallas no reimplementan.
- `src/app/(marketing)/entrar/page.tsx`: lee `next` de `useSearchParams`, lo pasa a `emailRedirectTo` en `signUp` como `${origin}/auth/callback?next=<safe>` y lo usa en el `router.push` del login. Tras `signUp` exitoso no navega: muestra la pantalla "revisá tu mail" (mismo componente, estado `enviado`). El `<span>` pasa a `<Link href="/entrar/recuperar">`. Se elimina la llamada a `sendWelcomeEmailAction`.
- `src/app/(marketing)/entrar/recuperar/page.tsx` (nuevo): un campo de mail, `resetPasswordForEmail(email, { redirectTo: ${origin}/auth/callback?next=/entrar/nueva-clave })`. La respuesta es siempre la misma, exista o no la cuenta.
- `src/app/(marketing)/entrar/nueva-clave/page.tsx` (nuevo): exige sesión (la deja el callback con el code de recovery); sin sesión redirige a `/entrar/recuperar`. Dos campos, `updateUser({ password })`, luego `/panel`.
- `src/app/(marketing)/entrar/actions.ts`: `sendWelcomeEmailAction` se borra. El disparador de la bienvenida pasa a ser **el callback**: tras un `exchangeCodeForSession` exitoso, `void notifyWelcome({ userId })`. Es el único lugar donde una sesión nace de un link de mail, y `mail_log` (`scope_key = "account"`) garantiza una sola bienvenida por cuenta aunque el callback se recorra de nuevo por recovery o por Google (T-041). No se usa un hook de GoTrue: no hay forma de encadenar `notifyWelcome` desde Postgres sin duplicar el transporte.
- Las tres pantallas nuevas llevan `metadata` con `robots: noindex` (R-11).

El implementador consulta Context7 (`/supabase/ssr` y `/websites/supabase`) para la firma vigente de `exchangeCodeForSession`, `resetPasswordForEmail` y `emailRedirectTo` antes de codear; esta spec no fija firmas.

### Criterios
1. Dado un registro con mail nuevo, cuando se envía el formulario, entonces no hay sesión, se ve "revisá tu mail" y en Mailpit hay un mail de confirmación de GoTrue cuyo link apunta a `/auth/callback`.
2. Dado ese link, cuando se abre, entonces hay sesión, se redirige a `/panel` y en `mail_log` existe una sola fila `welcome` para esa cuenta. Abrir el link dos veces no duplica la fila.
3. Dado un login con `?next=/leccion/abc`, cuando ingresa, entonces aterriza en `/leccion/abc`. Con `?next=https://evil.tld`, `//evil.tld` o `/\evil.tld`, aterriza en `/panel`.
4. Dado un usuario sin confirmar, cuando intenta `signInWithPassword`, entonces el mensaje dice "confirmá tu mail para entrar" y no hay sesión.
5. Dado `/entrar/recuperar` con un mail inexistente, cuando se envía, entonces la respuesta es idéntica a la de un mail existente y el tiempo de respuesta no delata la diferencia (la llamada a GoTrue se hace igual; GoTrue responde 200 en ambos casos).
6. Dado un link de recuperación, cuando se abre, entonces `/entrar/nueva-clave` acepta una clave nueva y el login siguiente funciona con ella. El link usado por segunda vez muestra el error neutro de c.7.
7. Dado `/auth/callback` sin `code` o con un `code` inválido, cuando se abre, entonces redirige a `/entrar?error=link` con "el enlace venció o ya se usó", sin detalle técnico.
8. Dado un registro con un nombre que viola ADR-009, cuando se envía, entonces el espejo `fullNameSchema` lo frena antes de `signUp` (ya existe; no debe perderse en el refactor).

### Cómo se verifica
- Vitest: `safe-next.test.ts` con tabla de casos (c.3), incluyendo `next` vacío, con query string y con fragmento.
- Playwright (`webApp/e2e/cuenta.spec.ts`): registro → link desde la API de Mailpit → `/panel`; recuperar → nueva clave → login. Es el flujo de punta a punta del ticket (R-14).
- `cd webApp/supabase && npm test` sin cambios de schema (no hay migración).
- `npx tsc --noEmit && npm run lint`.

9. **Dado** un login exitoso sin `?next=`, **cuando** termina, **entonces** `admin` cae en `/panel/admin`, `teacher` en `/panel/docente` y cualquier otro rol en `/panel` (transferido de T-038 c.8: hoy `entrar/page.tsx` siempre va a `/panel`). Con `?next=` válido, `next` gana.

### Riesgo
`email_sent = 2` por hora en `config.toml` y `max_frequency = "1s"`: en local, el segundo registro de la hora rebota con 429. Subirlo a `30` en local y dejar el comentario de que el valor de la nube se fija en el dashboard. El mensaje al usuario ante 429 es el mismo neutro de c.5 ("si existe una cuenta con ese mail, te llega un enlace"). Los usuarios ya existentes en local sin `email_confirmed_at` quedan afuera al activar D8: el seed de T-038 los crea confirmados.

## T-041 · Continuar con Google

**Agente:** `nerv-web` · **Nivel:** Strong · **Depende de:** T-040 (callback y `safeNext`)

### Por qué
D5. El botón existe, está inerte y promete "próximamente". Con el callback de T-040 el flujo OAuth es el mismo camino PKCE, no uno paralelo.

### Qué se toca
- `supabase/config.toml`: bloque `[auth.external.google]` con `enabled = true`, `client_id = "env(SUPABASE_AUTH_EXTERNAL_GOOGLE_CLIENT_ID)"`, `secret = "env(SUPABASE_AUTH_EXTERNAL_GOOGLE_CLIENT_SECRET)"`, `skip_nonce_check = false`. Nombres según la doc de Supabase (verificado en Context7 el 2026-10-21: `SUPABASE_AUTH_EXTERNAL_GOOGLE_CLIENT_SECRET`); el implementador reconfirma. Las dos variables van en `webApp/.env.local` y el CLI las toma del `.env` junto al `config.toml`: documentar en el plan qué archivo lee `supabase start` en este repo. En Google Cloud, redirect URI autorizado local: `http://127.0.0.1:54321/auth/v1/callback`.
- `src/app/(marketing)/entrar/page.tsx`: el botón llama a `signInWithOAuth({ provider: "google", options: { redirectTo: ${origin}/auth/callback?next=<safeNext> } })` con el cliente de `@/lib/supabase/client`. Se quita `disabled`, `title` y la opacidad. El SVG de Google se mantiene (inline, no raster).
- Sin migración. `profiles` nace por `handle_new_user` igual que por mail: Google deja `full_name` en `raw_user_meta_data`, que es la clave que el trigger ya lee. El rol sigue siendo el literal `student`.
- Vinculación: cuando el mail de Google ya existe como cuenta con contraseña, GoTrue vincula la identidad al usuario existente si el proveedor reporta el mail verificado (Google lo hace). No hay `insert` en `auth.users`, no hay segundo `profiles`, no hay segunda bienvenida (`mail_log`). Es el comportamiento por defecto; `enable_manual_linking` queda en `false`.

### Criterios
1. Dado un mail que no existe, cuando entra con Google, entonces pasa por `/auth/callback`, tiene sesión, existe `profiles` con `role = student` y `full_name` del proveedor, y hay una fila `welcome` en `mail_log`.
2. Dado un mail ya registrado con contraseña y confirmado, cuando entra con Google, entonces entra a la misma cuenta (mismo `profiles.id`), `auth.identities` tiene dos filas para ese usuario, y la contraseña sigue funcionando.
3. Dado `/entrar?next=/cursos/x`, cuando entra con Google, entonces aterriza en `/cursos/x`; con un `next` externo aterriza en `/panel`.
4. Dado que el usuario cancela en la pantalla de Google, cuando vuelve, entonces ve el error neutro de T-040 c.7 y no queda sesión.
5. Dado que no hay credenciales en `.env.local`, cuando se corre la suite, entonces el test unitario del botón pasa igual (verifica provider y `redirectTo`), y Playwright marca el flujo Google como `skip` con el motivo explícito.

### Cómo se verifica
- Vitest: test del componente del botón con `createClient` mockeado, afirmando `provider: "google"` y que `redirectTo` termina en `/auth/callback?next=` con el valor saneado (c.5).
- Con credenciales del PO: c.1 a c.4 a mano contra el stack local, registrados en el handoff con el `profiles.id` y las dos filas de `auth.identities` (c.2 se prueba, no se asume).
- `npm test` en `supabase/` (sin cambios), `tsc`, `lint`.

### Riesgo
Local sin credenciales reales deja c.1 a c.4 sin ejecutar: el ticket queda "cableado y testeado en unidad", y el handoff lo declara así, no como Done pleno. Si GoTrue local falla la verificación de nonce, `skip_nonce_check = true` se permite solo en local y con comentario; nunca se propone para la nube. Un `full_name` de Google que dispare `profiles_locator_guard` (ADR-010) aborta la creación del usuario entero: el test de c.1 incluye un nombre con punto y dominio ("Ana Perez.com") para medir si pasa; si no pasa, el plan lo resuelve con `coalesce` a `''` en `handle_new_user`, no relajando el guard.

## T-042 · Perfil editable con avatar

**Agente:** `nerv-arquitecto` (migración, Storage) + `nerv-web` (página) · **Nivel:** Strong · **Depende de:** T-039; ordenado tras T-041 por archivos compartidos en `entrar/`

### Por qué
D6 cierra Q-11: nombre, avatar, bio, teléfono, fecha de nacimiento, editables por la persona. `full_name` y `bio` ya existen con grants y guard; faltan los tres campos nuevos, el bucket y la página. La fecha de nacimiento es dato sensible: se borra a voluntad y no sale en ninguna página pública ni a otros usuarios.

### Migración `20261021120000_0026_profile_private_fields.sql`
- `alter table public.profiles add column phone text, add column birth_date date, add column avatar_path text;`
- CHECKs: `phone is null or phone ~ '^\+?[0-9][0-9 ()-]{5,19}$'`; `birth_date is null or (birth_date > date '1900-01-01' and birth_date <= current_date)`; `avatar_path is null or avatar_path ~ '^avatars/[0-9a-f-]{36}/[a-z0-9-]+\.(jpg|png|webp)$'`.
- Grants (R-1): `grant update (phone, birth_date, avatar_path) on public.profiles to authenticated;` La fila la sigue filtrando `profiles_update_self`. **Sin `grant select` de `phone` ni `birth_date` a `anon` ni `authenticated`**: un grant de columna no distingue filas y `profiles_read_public` ya deja leer las filas de docentes a cualquier sesión. `avatar_path` sí se lee (`anon, authenticated`): es un path opaco, no un dato personal, y la ficha pública lo necesita.
- Lectura propia: función `public.my_private_profile()` `security definer`, `set search_path = ''`, `returns table (phone text, birth_date date)` filtrada por `auth.uid()`, con `revoke execute ... from public` + `grant execute to authenticated` (regla de 0005:153). Es la única vía de lectura de esos dos campos desde el cliente de sesión.
- Guard trigger (R-7, ADR-011) `profiles_avatar_path_guard` before update: `new.avatar_path is null or new.avatar_path like 'avatars/' || new.id::text || '/%'`. Sin esto, un usuario apunta su avatar al archivo de otro. Checklist de ADR-011 y caso de alcanzabilidad en `guard-reachability.test.mjs` (la meta-aserción de `4bd9f27` lo exige).
- Storage, en bloque `do $$ ... if to_regclass('storage.objects') is not null then ... end if $$` para que PGlite (sin schema `storage`) aplique la migración igual: `insert into storage.buckets (id, name, public) values ('uploads','uploads',false) on conflict do nothing;` y policies sobre `storage.objects` para `authenticated`: insert/update/delete con `bucket_id = 'uploads' and (storage.foldername(name))[1] = 'avatars' and (storage.foldername(name))[2] = auth.uid()::text`; select con la misma condición (el dueño ve lo suyo; la lectura pública no pasa por acá). Espejo en `config.toml`: `[storage.buckets.uploads] public = false, file_size_limit = "5MiB", allowed_mime_types = ["image/jpeg","image/png","image/webp"]` (el bucket es compartido con T-047; el tope de 2 MB para avatares lo impone el servidor).
- `role`, `years_practice`, `formations`, `testimonials` no cambian de grants.

**Servir el avatar:** bucket privado + URL firmada (`createSignedUrl`, 1 h) generada en el Server Component que ya lee el perfil, con el cliente de sesión para el propio usuario y con `service_role` para la ficha pública de `/guias/[slug]` y las tarjetas de curso. Un solo bucket y un solo juego de policies (S-D); un bucket público listaría `avatars/<uid>/` a cualquiera y la URL firmada cuesta una llamada por render, que la ficha ya paga en la consulta de `guias.ts`.

### Qué se toca
- `src/app/(app)/panel/perfil/page.tsx` + `actions.ts` (nuevos). Cae bajo `(app)/layout.tsx` (sesión) y fuera de los layouts de rol: la comparten los tres roles. `noindex` (R-11).
- Server Actions: `updateProfileAction` (full_name, bio, phone, birth_date) con zod en `src/lib/validation/profile.ts` (reusa `fullNameSchema` y `noLocator` para bio, R-3); `clearBirthDateAction`; `uploadAvatarAction(FormData)`: valida tamaño ≤ 2 MB y tipo por magic bytes (no por extensión ni `Content-Type`), nombre `avatars/<uid>/<uuid>.<ext>`, sube con el cliente de sesión (la policy de Storage hace de segunda defensa), actualiza `avatar_path`, borra el objeto anterior; `removeAvatarAction`: borra objeto y pone `null`.
- Nav: link "Mi perfil" en `src/components/layout/Nav.tsx` (menú de sesión) y en las cabeceras de `panel/page.tsx`, `panel/docente/page.tsx`, `panel/admin/page.tsx`.
- `src/lib/server/guias.ts` y `/guias/[slug]/page.tsx`: suman `avatar_path` y lo renderizan en el bloque "Portrait" en lugar del glifo cuando existe; el `select` no incluye `phone` ni `birth_date` (no tendría grant, pero el test lo afirma igual).
- `src/lib/server/auth.ts`: `getCurrentUser` suma `avatarPath` para el menú.

### Criterios
1. Dado un usuario con sesión de cualquier rol, cuando abre `/panel/perfil`, entonces ve nombre, bio, teléfono, fecha de nacimiento y avatar propios y puede guardar cada uno; el rol no se muestra como editable.
2. Dado un PATCH por PostgREST a `profiles` con `phone` sobre el `id` de otro usuario, cuando se ejecuta como `authenticated`, entonces afecta 0 filas y el valor del otro no cambia (RLS), y el caso queda en `rls-mutation.test.mjs` y en `b1-postgrest-attacks.sh` (R-6).
3. Dado un `select birth_date` o `phone` sobre `profiles` como `anon` o como otro `authenticated`, cuando se ejecuta, entonces falla con `42501`; `has_column_privilege` para ambos roles devuelve `false` en ambas columnas (test de grants).
4. Dado `my_private_profile()` llamada por el dueño, cuando se ejecuta, entonces devuelve su fila; llamada por `anon` falla por falta de EXECUTE.
5. Dado un `update avatar_path = 'avatars/<otro-uid>/x.jpg'` sobre la fila propia, cuando se ejecuta, entonces el guard lo rechaza; con `avatars/<propio-uid>/x.jpg` pasa (camino legítimo, ADR-011).
6. Dado un archivo de 2 MB + 1 byte, o un `.jpg` cuyos bytes son un PDF, cuando se sube, entonces el servidor lo rechaza con mensaje y no hay objeto en el bucket.
7. Dado un avatar subido, cuando se abre `/guias/<slug>` como `anon`, entonces se ve la imagen vía URL firmada y el HTML no contiene `birth_date` ni `phone`; cuando el usuario lo borra, la ficha vuelve al glifo y el objeto no existe más.
8. Dado un usuario con fecha de nacimiento cargada, cuando la borra, entonces queda `null` y la página no la reconstruye desde ningún otro lado.
9. Dado un `name` de bio o nombre con localizador (ADR-009/010), cuando se guarda, entonces el espejo zod lo frena con mensaje y, si se saltea el espejo, el CHECK y el guard de `0025` lo frenan en la base.
10. Dado un POST a Storage con path `avatars/<otro-uid>/x.jpg`, cuando se ejecuta por HTTP con el JWT de un usuario, entonces responde 4xx (ataque en `b1-postgrest-attacks.sh`; no es verificable en PGlite y el handoff lo declara).

### Cómo se verifica
- `supabase/tests/profile-private-fields.test.mjs` (nuevo): c.2 a c.5 y c.9, con control negativo que revierte el grant y muestra que el ataque pasa (patrón de `rls-mutation`).
- `guard-reachability.test.mjs`: caso del guard nuevo.
- `locator-free-text.test.mjs`: `avatar_path` entra a la clase (legible por `anon`, escribible por `authenticated`); el CHECK de formato ya excluye localizadores, pero el test de paridad exige un `%_no_locator` explícito: agregarlo.
- `b1-postgrest-attacks.sh`: c.2, c.3 y c.10 por HTTP.
- Vitest: esquemas zod (teléfono, fecha, magic bytes). Playwright: editar perfil, subir avatar, borrar fecha.
- `npm test` (supabase), `tsc`, `lint`.

### Riesgo
`phone` y `birth_date` sin `SELECT` para el cliente obligan a que toda lectura pase por `my_private_profile()`; si el verificador prefiere una tabla `profile_private` con RLS propia, el cambio es local a esta migración y no toca la página. La URL firmada caduca a la hora: una ficha cacheada por más tiempo mostraría un avatar roto, así que `/guias/[slug]` no fija `revalidate` mayor a 3600. El `do $$ ... $$` para Storage hace que la suite de PGlite no pruebe las policies del bucket: el harness HTTP es el único verificador de c.10 y el handoff lo tiene que decir con esas palabras.
